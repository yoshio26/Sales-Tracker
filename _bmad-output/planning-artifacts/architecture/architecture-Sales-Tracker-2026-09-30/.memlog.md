- (constraint) Sales is the primary capability; inventory supports sales through stock movements and low-stock warnings. Must-have scope: login with roles, product list, multi-item sales, filtered sales history, automatic stock deduction, and low-stock warning. Should-have scope: dashboard, CSV export, and void/refund with reason. Nice-to-have scope: PDF outputs and moving-average forecast. Full supplier management and purchase orders are out of scope; stock-in entry is sufficient.
- (constraint) Roles: Admin manages users and everything else; Manager manages products and views reports/dashboard; Cashier records sales only.
- (constraint) Sale item unit_price is a historical snapshot. Stock is derived from stock_movements, with one movement per sale item and transactional consistency across sale, items, and movements.
- (direction) Architecture spine must also feed capstone documentation: ERD, use cases, system architecture chapter, and a week-by-week implementation plan. No C4 diagrams or team walkthrough unless required by the school.
- (constraint) Revised scope supersedes the earlier sales and inventory scope: dashboard, passwordless email login, user-owned products, spending records, and dashboard only. Dropped: sales recording, multi-item sales, void/refund, forecasting, and three-role model.
- (constraint) Authentication uses passwordless email login: server-generated 6-digit code via crypto.randomInt, hashed at rest, single-use, expires after 10 minutes, locks after 5 failed attempts, then creates or finds the user and establishes an HTTP-only session cookie.
- (constraint) Every authenticated API operation is scoped to the session user_id. Users have identical permissions and cannot access another user's products, expenses, or dashboard aggregates.
- (constraint) Chosen technology direction: TypeScript, React TSX with CSS, Express, PostgreSQL on the developer's machine, Nodemailer, SMTP-backed email delivery, and session cookies. Development email uses Mailpit; demonstration or real email may use an external SMTP provider configured through environment variables.
- (constraint) Dashboard shows total spending for current month and all time, spending by product and category, spending over time, and product add/edit management. Proposed tables: users, login_codes, products, expenses; expenses represent purchase costs and remain available for explicit spending records.
- (constraint) Sending login codes is rate-limited, initially 3 requests per 10 minutes per email, to prevent email abuse.
- (decision) Allowlist authentication is adopted. Only emails present in allowed_emails may receive a login code; unapproved and approved requests return the same generic response, and unapproved requests send no email. All allowlisted users have identical permissions and see only their own data. The allowlist may be maintained through a seed script and an allowed_emails table.
- (decision) Rate limiting applies before allowlist disclosure so repeated requests for approved or unapproved addresses cannot be used for probing or email abuse.
- (decision) Expenses are the authoritative spending ledger. Each expense records user_id, product_id, amount actually paid, quantity bought, note, and spent_at; dashboard totals and charts sum expenses only. Products are a catalog and do not track stock, so products.quantity is removed. Product edits never alter historical expense totals.
- (constraint) Core relational shape is users, allowed_emails, login_codes, products, and expenses. Product category remains a product attribute for category-based reporting; expense rows retain the product relationship and historical purchase facts.
- (decision) Expense history snapshots are adopted. At insert time, the server reads the referenced product and copies its current name and category into product_name_snapshot and category_snapshot. product_id remains a reference, while spending-by-product and spending-by-category reports group by snapshot columns. The client never submits snapshot values; product edits or archival cannot change historical reports.
- (decision) Sessions are PostgreSQL-backed. After successful code verification, the server creates a session row and sets an opaque cryptographically random session identifier in an HTTP-only cookie; the cookie contains no user data. Sessions last 7 days, are deleted on logout, use SameSite=Lax, and use Secure whenever served over HTTPS. Every API route resolves the session to user_id and scopes all data queries to that user.
- (decision) The application is a modular monolith with layered internals: one repository and one deployable app containing the React client, Express API, and PostgreSQL database. Feature modules are Auth, Products, Expenses, and Dashboard. Each module has routes for HTTP and Zod validation, services for business rules, and data access for persistence. Routes never access the database directly; modules communicate through services; microservices are out of scope.
- (decision) Prisma is the default data-access layer and prisma migrate owns schema migrations. Raw SQL is allowed only in Dashboard data access for monthly, product, and category aggregates that Prisma cannot express cleanly; raw queries must use Prisma tagged-template with parameterized values and no string concatenation. Routes and services never import Prisma directly; all persistence access stays within module data-access layers.
- (version) Official technology checks performed 2026-09-30: Express site reports 5.2.1; PostgreSQL current documentation reports 18.6; Prisma official documentation is for ORM v6 and shows Prisma 6.19.3 package examples; Nodemailer site reports 10 requires Node.js 20 or later; Zod site reports Zod 4 stable. React and TypeScript version pins remain pending official documentation confirmation.
- (decision) Frontend tooling is Vite with the official react-ts template: React and TypeScript with TSX and CSS Modules. Vite is used for frontend development and production builds only. Development proxies /api to Express so the browser uses one origin; production serves Vite's static build through Express on one port. Create React App is not used. Exact package versions are pinned in package.json and the lockfile.
- (decision) Expenses are editable and deletable through validated server operations scoped to the session user_id. Users may change amount, quantity, note, and spent_at; normal edits preserve product_name_snapshot and category_snapshot. If product_id changes, the server re-snapshots both values from the newly selected product. Deletes set deleted_at instead of removing rows, and every dashboard query excludes deleted expenses. Products are archived with active=false rather than deleted so historical references remain valid.
